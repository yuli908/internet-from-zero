# 09 可行性风险（最不可行的三处与替代方案）

判定标准:**"真实"与"可玩/可读"同时成立才算可行**。
只要有一条做不到,就必须换方案,而不是用动画糊过去。以下三处是本次规格里
**明确不建议硬做**的,理由与替代方案都给出可验证的边界。

---

## 风险 1:门级全展开的完整 CPU,实时 + 可读

### 为什么不可行

- **规模**:一个 8 位 CPU 若真按门级展开(8×8 寄存器堆 = 64 个 DFF、ALU ≈ 500 门、
  控制单元 ≈ 300 门、译码/布线 ≈ 200 门),总量 **1000–2000 门**。
- **事件量**:每时钟周期几乎全部翻转 ≈ `3 × 1500 = 4500 事件/周期`。
  按 06 的估算,原生 5 ms 只能吃 8000 事件/tick → 一个周期就吃掉半帧;
  而教学必须**降速观看**,一帧一个周期意味着 60 个周期/秒,程序根本跑不完。
- **可读性(真正致命的一条)**:1500 根线 + 1500 个门在一屏里,玩家**无法定位**
  "现在 PC 在做什么"。真实芯片的版图是靠层次化抽象读的,不是靠"全展开"。
  全展开的结果是"看起来很硬核,实际学不到东西"。

### 替代方案(两层视图)

1. **主线用结构级(L4)**:微码状态机 + 数据通路宏单元(寄存器堆、ALU、RAM)。
   每个微状态高亮对应通路,延迟由 03 的实测值兑现(如 ALU 26 tick)。
2. **门级只做"器件实验台"**:玩家在独立沙盘里搭 1 位全加器、4 位计数器、2:1 选择器,
   规模 ≤ 200 门,能全展开、能看波形、能造毛刺。
3. **桥接视图**:在 CPU 视图里点某个宏单元 → 弹出该单元的门级展开(只读、≤ 500 门),
   并标注"此展开由真实门级实现生成,与其等效性已测试"。

### 对教学的影响(必须写进 UI)

- 玩家**看不到** CPU 每个周期的每一根线;能看到的是"指令 → 微状态 → 数据通路"。
- 这不损失核心结论(取指/译码/执行、时钟周期与延迟的关系),但损失"全门级视野"。
- 明确禁止:把宏单元动画说成"门级仿真"。正确表述:"该单元已被折叠,延迟与真值由
  门级实现实测"。

### 验收边界

- 实验台:≤ 200 门时 60 FPS、4 tick/帧不掉帧(GDScript 亦可)。
- CPU 视图:宏单元数 ≤ 12 个,单屏可读(每个都有名字与位宽)。
- 等效性:每个宏单元必须有"门级实现 vs 宏单元"的等价测试(08 第 2 节"等价性"层)。

## 风险 2:游戏内真 TCP/IP,并与真实主机互通

### 为什么不可行

- **语义正确性无法自证**:真 TCP 的正确性依赖窗口、重排、拥塞控制、路径 MTU、
  定时器精度等几十个交互项。游戏内自写一套,既不能证明它对,也不能与真实内核互通
  (除非用 socket 桥接,那就不是"游戏内实现")。
- **教学反而变差**:真 TCP 的因果链被参数淹没——玩家丢一个包,看到的是"cwnd 变了、
  重传了、窗口滑了",但**看不到"为什么等这么久"**。
- **确定性冲突**:真 TCP 的 RTT 估计依赖实时时钟;本作要求整数 tick 全序可复现(02)。
  把真实时钟塞进来会直接破坏回放。

### 替代方案

1. **游戏内只做 TCP-lite**(04 第 6.2 节):段编号、固定窗口、超时 + 指数退避、
   无拥塞控制、无乱序缓存。已实测:送达 5 段 / 12 次重传 / 退避 `10→20→40` / 5 次后 ABORT。
2. **真实互通交给 L7 桥接**:宿主侧伴生进程用**系统标准 socket**收发,
   游戏只负责"应用字节流 → 教学协议 → 桥"。桥的边界在 01 第 9 节已写明。
3. **对照教学**:同一份数据,分别用"教学协议"和"桥接的真实 TCP"跑,
   让玩家比较时序图差异(这是真 TCP 唯一值得看的部分)。

### 对教学的影响

- 玩家学到"可靠传输的因果"(丢 → 等 → 退避 → 重发),学不到"拥塞控制"。
- **禁止文案**:"你写的协议已在公网运行""你在用真实 TCP"。
  允许文案:"你的协议通过本机伴生进程转发到一个真实端口;真实链路用的是系统协议栈。"
- 若后续要教拥塞控制,必须新增独立关卡(慢启动/拥塞避免的状态表),不得偷改 TCP-lite。

## 风险 3:游戏内"安全加密"

### 为什么不可行

- **确定性 vs 随机性**:存档必须可复现(02),因此**没有真随机源**。
  一次性密码本的安全前提直接不成立(05 第 4.2 节,实测密钥复用即泄露)。
- **可教学性 vs 强度**:为了"一屏能穷举",密钥空间必须小。
  实测 Feistel 玩具密钥空间 256(命中 16 个候选)、RSA `n=3233` 毫秒分解(53×61)。
  强度与可读性在这里是**直接冲突**的,不是工程优化能解决的。
- **没有密码分析能力**:自制算法无法被证明安全;声称安全即是欺骗。

### 替代方案

1. **只教"机制 + 破法"**:每一级都必须能被上一级的工具打破(凯撒 26 次穷举、
   OTP 复用泄露、Feistel 穷举、RSA 分解)。这是本作唯一诚实的加密教学。
2. **强度边界写死**(05 第 8 节):游戏内不得声称安全;UI 禁词表见 05 第 9 节。
3. **真要"安全通信"→ 交宿主**:经 L7 调用系统 TLS,并在 UI 标注
   "此段由宿主标准库提供,游戏内只做转发,不实现也不验证密码学"。

### 对教学的影响

- 玩家理解"为什么弱""密钥空间不等于强度""公钥的不对称来自数学难题的规模",
  但不具备"构建安全系统"的能力(那需要密钥管理、侧信道、协议设计,超出本作范围)。
- 这不会让课程变浅:相反,它能纠正"自己写个加密就安全了"这一最常见的错误直觉。

## 附:第四处风险(次要,但会影响观感)

**10,000 门级别的电路可视化**。06 允许原生跑到 1 万门,但"画出来"不可读:
一屏 1 万根线等于噪声。替代:分区视图(每区 ≤ 300 门)+ 缩略图 + 探针书签,
只渲染"可见区 + 相邻 1 跳"。这条不改变仿真语义,只改变呈现,因此优先级低于前三处。

---

## 总结(给决策者)

| 风险 | 硬做的后果 | 采用替代后的损失 |
|---|---|---|
| 门级全展开 CPU | 掉帧 + 玩家读不懂 | 失去"全门级视野",保留全部核心结论 |
| 真 TCP/IP | 语义不可证 + 破坏确定性 + 因果被淹没 | 失去拥塞控制,保留可靠传输因果 |
| 游戏内安全加密 | 必须撒谎 | 失去"如何做安全系统",保留"为什么弱" |

三处的共同点:**它们都不是"性能不够",而是"真实性目标与教学/确定性目标互斥"**。
本规格选择保真度可以降、语义不能假;能少做一层,但不做假动画。
