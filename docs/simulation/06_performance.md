# 06 性能预算（Godot 主线程 / 器件上限 / 分块降采样）

**先说清楚**:本文件的绝对数字分两类,读者必须区分:

| 类别 | 来源 | 可信度 |
|---|---|---|
| 事件吞吐 | Python 参考实现**实测**(见 [verify_report.md](file:///D:/ai%20lm/internet_from_zero/docs/simulation/ref/verify_report.md)) | 实测,但**不是 Godot** |
| GDScript / GDExtension 系数 | **估算**(按 3–8 µs / 80–200 ns 每事件) | 估算,**必须用工程内基准关校准** |
| 场景上限 | 由上面两项反推 | 目标值,允许下调,不允许上调而不校准 |

> 任何"Godot 能跑 X 万门"的说法,在本文件里都是**估算**。如果有人给出精确到个位数的
> 主线程预算,那一定是假的。工程必须实现第 6 节的自动校准,让上限变成运行时事实。

## 1. 帧预算(60 FPS)

| 项 | 预算 | 说明 |
|---|---|---|
| 整帧 | 16.6 ms | 60 FPS |
| 渲染 + UI + 音频 | 8.0 ms | 不属于仿真 |
| **仿真(事件引擎 + 网络 + CPU 微码)** | **5.0 ms** | 本文件约束的对象 |
| 余量 | 3.6 ms | 防抖动、防 GC 尖峰 |

30 FPS 目标(低端机)时:仿真预算 **10 ms**。仿真预算**不随帧率线性放大**,
因为它还要与"每帧推进多少 tick"一起决定观感(见第 5 节)。

## 2. 从"事件吞吐"到"器件上限"

### 2.1 实测锚点(Python)

| 门数 | 事件数 | 耗时 | 事件/毫秒 |
|---|---|---|---|
| 64 | 486 | 1.14 ms | 427 |
| 256 | 1926 | 4.70 ms | 409 |
| 1024 | 7686 | 21.59 ms | 355 |

> 多次运行的实际区间约 **244–427 事件/毫秒**(Python 受 GC 与机器负载影响,波动近 2 倍)。
> 这正说明:上限不能按"某一次的好成绩"来定,必须按**实测曲线 + 安全系数**来定。
> 1024 门时吞吐下降,是因为堆操作与回调开销占比上升 —— 事件数不可线性外推。

### 2.2 单事件成本(估算,需校准)

| 实现 | 成本/事件 | 5 ms 可处理事件 | 备注 |
|---|---|---|---|
| GDScript | 3–8 µs | 600–1600 | 动态类型 + 堆分配;估算是**保守悲观**值 |
| C++ GDExtension | 80–200 ns | 25k–60k | 现代 CPU + 无锁桶队列;估算值 |

### 2.3 一个"翻转门"产生多少事件

一个输入翻转的门 ≈ **3 个事件**(1 次求值调度 + 1 次求值 + 1 次写出触发下游)。
因此:

```
每 tick 可翻转门数 ≈ (每帧事件预算 / 每帧 tick 数) / 3
```

以默认 **4 tick/帧**、5 ms 预算:

| 实现 | 事件/帧 | 事件/tick | 可翻转门/tick | 建议总门数上限 |
|---|---|---|---|---|
| GDScript | 1000 | 250 | ~80 | **≤ 200 门** |
| GDExtension | 33000 | 8000 | ~2700 | **≤ 10000 门** |

> "总门数上限" > "可翻转门数",因为大部分门在大多数 tick 不翻转(静态电路)。
> 这个比值由场景决定,工程必须按"最坏全翻转"来验,按"实测利用率"来放。

### 2.4 触发器

DFF 只在**时钟边沿**产生事件(边沿 1 + 采样 1 + 写出 1 + 下游 1 ≈ 4 事件/边沿)。
一个 CPU 的寄存器堆若按门级展开会瞬间爆预算,因此:

| 对象 | GDScript | GDExtension | 依据 |
|---|---|---|---|
| DFF 总数 | ≤ 200 | ≤ 8000 | 8000×4 = 32k 事件/边沿 ≈ 5 ms |
| 寄存器 | 用 D17 宏单元 | 同左 | 寄存器不展开成 DFF 阵列 |

**结论**:CPU 场景**永远**用结构级(L4 微码 + D17/D20/D23 宏单元),
不把 8 位 CPU 展开成 1000+ 门。门级只在"单器件教学关"里展开。

## 3. 各层上限(权威值,01 的表格与此一致)

| 层 | 上限 | 条件 | 超限行为 |
|---|---|---|---|
| L0a 模拟电平 | 64 节点 | 仅教学沙盘;固定子步长 | 禁止进入下一关,提示"关闭模拟层" |
| L1 门级 | 200 / 10000 门 | GDScript / 原生,60 FPS,4 tick/帧 | 超限→自动转 LOD 宏单元(见 5.4) |
| L2 组合模块 | 由 L1 组合 | 单模块 ≤ 2000 门(如 8 位 ALU) | 构建期检查,超限报错 |
| L3 时序 | 200 / 8000 DFF | 同上 | 超限→必须用寄存器宏单元 |
| L4 CPU | 1 个 CPU,64 KiB 存储 | 微码周期精度 | 多 CPU 场景需分场景加载 |
| L5 总线 | 16 个主设备 | 固定优先级仲裁 | 超限报错 |
| L6 网络 | 256 节点 / 4096 包在途 | 见 3.1 | 超限→拒绝新连接,提示 |
| L7 桥接 | 4 个连接 | 宿主 socket | 超出排队 |

### 3.1 网络层的成本

网络层事件很稀(每包 6–10 个事件),真正的成本在**路由计算**:

- `compute_routes()` 是 O(V²)=65,536 次比较(256 节点),**必须原生实现**。
  在 GDScript 里单次约 1–3 ms,一次拓扑变化就会吃掉半个帧预算。
- 4096 包在途 × 96 B ≈ 0.4 MB;事件队列峰值 ≈ 4096×2 ≈ 8k 项 → 必须在原生队列里。
- 因此:**网络仿真整体走 GDExtension**,GDScript 只负责 UI(抓包器、拓扑图)。

## 4. 内存估算(单场景)

| 对象 | 单项 | 上限 | 小计 |
|---|---|---|---|
| 门 | 48–64 B | 10,000 | ~0.6 MB |
| 线网 | 40 B + 位串 | 30,000 | ~2 MB |
| DFF/寄存器 | 64 B | 8,000 | ~0.5 MB |
| 事件队列 | 24 B/项 | 100,000 | ~2.4 MB |
| 网络节点路由表 | 2 KB/节点 | 256 | ~0.5 MB |
| 在途包 | 96 B/包 | 4,096 | ~0.4 MB |
| 存储器 | 1 B/字 | 64 KiB | 64 KB |
| Trace 环形缓冲 | 32 B/条 | 1,000,000 | ~32 MB(可关) |

- **Trace 是最大项**:默认只保留最近 50k 条(≈1.6 MB),完整 trace 只在"录制回放"模式开启。
- 存档(canonical JSON)对 10k 线网 ≈ 250–300 KB,gzip 后 ≈ 40–60 KB。

## 5. 降采样与分块(按优先级)

### 5.1 时间分片(首选,不损失保真度)

- 每帧只跑 `min(剩余预算, k 个 tick)`。跑不完就**下一帧继续**,轨迹完全不变。
- 表现:慢放。玩家看到的是"波形成了一个个 tick 推过去",这恰好是教学想要的。
- **禁止**:为了追帧率而丢弃事件 —— 那会让状态与回放不一致(02 第 3 节)。

### 5.2 速度档位(玩家可选,不是自动降级)

| 档位 | tick/帧 | 适用 |
|---|---|---|
| 0.25× | 1 | 讲边沿、讲建立时间 |
| 1× (默认) | 4 | 一般组装 |
| 4× | 16 | 跑 CPU 程序 |
| 16× | 64 | 网络收敛演示(可开"跳过渲染") |

档位只影响"每帧推多少 tick",**不改变轨迹**(02 第 1 节)。

### 5.3 空间分块(仅在需要时)

- 把电路按"寄存器边界"切成若干子图,子图内部独立 settle,子图间只在 tick 边界传值。
- **代价**:跨块边界的毛刺会被吃掉(边界变成同步点)→ 冒险教学必须**关掉分块**。
- 因此分块的开关必须是**场景属性**,存档里记录 `partition: on/off`,回放时不得切换。

### 5.4 LOD:宏单元(有代价的省事件)

- 当模块规模超过阈值(默认 500 门),构建期用**真实门级实现**跑一次全输入组合,
  测出 `t_settle` 与真值,然后替换为"延迟 = 实测值"的宏单元。
- 关键约束:宏单元的延迟**必须来自实测**,不能填常数;且 UI 必须标注"宏单元(已折叠)"。
- **禁止**:把宏单元说成"仿真过了"。它仿真过,但玩家看不到内部冒险。
- 本规格已用这条路径的正是 D20 ALU(结构级 + 实测 26 tick)与 D23 RAM(宏单元)。

### 5.5 降级阶梯(触发条件与提示)

| 触发 | 自动动作 | 玩家可见 | 影响 |
|---|---|---|---|
| 单帧仿真 > 5 ms 连续 30 帧 | tick/帧 降一档 | "仿真降速中"角标 | 无(轨迹不变) |
| 仍超 | 关闭 Trace 全量录制 | 角标 + 提示 | 回放精度下降 |
| 仍超 | 提示切"仅仿真视图"(关渲染特效) | 明确提示 | 观感下降 |
| 单 tick 事件 > 50k | 报 `SimLimitExceeded` | 弹窗"电路自激/环" | **不静默** |

## 6. 工程必须做的校准(交付条件)

实现方必须在主工程内提供一个**基准关**(不进主线剧情),做三件事:

1. 生成 N 个门(1k/10k/50k)的链式电路,全翻转,记录 `事件/秒` 与 `帧耗时`;
2. 同一场景用 GDScript 与 GDExtension 各跑一次,记录系数;
3. 把结果写进 `bench_report.json`,启动时读取;若实测上限低于本文档,
   **以实测为准并下调第 3 节表格**(同时改 01 与本文件,并重录 08 的 golden)。

> 没有这个基准关,第 3 节的上限就只是"愿望"。本文档不把愿望写成事实。

## 7. 已知不适用

- 本预算**不含**渲染 10 万根线的开销。示波器/电路视图的绘制成本另算:
  建议"可见线网 ≤ 2000 根",超出用缩略图 + 分区视图(见 09)。
- 本预算**不含**存档序列化。10k 线网的 canonical JSON 序列化约 3–8 ms(GDScript),
  必须放到后台线程或"暂停时"执行,不得在游戏帧内做。
- 本预算**不含**音频/语音,与仿真无关。
